**Related:** [LLP 0001 Trust Model and Security Principles](0001-trust-model.principles.md), [LLP 0006 Config Schema, Loading, and Monorepo Routing](0006-config-schema-loading-routing.explainer.md), [LLP 0008 Review Sources and Reporters](0008-sources-and-reporters.explainer.md), [LLP 0009 Adopting ecr: Templates, Scaffolded CI Workflows, and Prompt Rules](0009-adoption-templates-and-ci-workflows.guide.md)

The command layer (`src/cli.ts`, `src/commands/*.ts`) is thin by design: it parses argv, assembles a `ReviewOptions`, and hands the actual multi-agent execution to `runReview` (LLP 0002). This doc records the decisions that live *only* in the command layer — where the trust boundary between "you at a terminal" and "a PR in CI" is drawn, why flag combinations are rejected instead of merged, and why the CI path fails closed. The code says what each command does; this says why it refuses the shortcuts.

## Command Dispatch and Conventions

`cli.ts` is argv dispatch and nothing else. With no subcommand, or an `argv[2]` that starts with `-`, it defaults to `ecr review` [observed: `src/cli.ts:38-41`, `if (!sub || sub.startsWith("-")) { await reviewCommand(...) }`]. That default is a real trade-off: it makes `ecr --pr 5` a review invocation, so a leading-flag typo silently routes into `reviewCommand` rather than the unknown-command error. The constraint that falls out of it — any new *global* flag must not collide with a `review` flag name — is worth stating because dispatch will not catch the collision for you.

Two conventions hold across every command file, both [observed: `AGENTS.md` Conventions, verified across command files]:

- Commands set `process.exitCode` explicitly and never call `process.exit()`. Exit is a value the command reports, not a control-flow jump, so `finally` cleanup (source disposal, trusted-root removal) always runs.
- Every subprocess spawn goes through `src/core/exec.ts` (`execFile` with argument arrays, never a shell string), and every binary invoked by name (`opencode`, `claude`, `gh`, `git`) is resolved to a trusted absolute path first, never a bare name searched on `PATH` from a possibly-untrusted cwd. The one deliberate exception is `setup-auth`'s two interactive `spawnSync` logins (`claude setup-token`, `opencode auth login`), which need `stdio: "inherit"` for the browser flow — see [doctor and setup-auth](#doctor-and-setup-auth). It is the explicit exception to "always exec.ts", not an accidental bypass.

`review`, `ci`, and `dismiss` all `chdir` to the resolved repo root before doing work, because the OpenCode server roots itself at `process.cwd()`; running from the repo root is what lets agents read the whole checkout and lets diff paths resolve correctly [observed: `src/commands/review.ts:167-172` comment; same pattern `src/commands/ci.ts:127-129`, `src/commands/dismiss.ts:82-85`].

## ecr review: Local Trust and Flag Rules

`ecr review` is the human-at-a-terminal entry point, and its defining decision is that the *person running it is the trust principal*. Config always loads from your local checkout, even with `--pr`: the PR head is materialized only as read content (scrubbed of ambient runtime config), never as policy [observed: `src/commands/review.ts:47-48` USAGE, "Config always loads from YOUR checkout in local runs — you are the trust principal here"]. This is the mirror image of `ecr ci`, and the split is the whole point — the same tool is safe locally *because* it is a different trust model in CI.

Flag exclusivity is rejected outright, never silently resolved, because silently ignoring one side of a combination discards the diff range the user actually asked for [observed: `src/commands/review.ts:306-327` `validateArgs`]:

- `--pr` cannot combine with `--base`/`--head`/`--staged` (a PR is reviewed by its diff, not a local ref range).
- `--staged` (index vs HEAD) is mutually exclusive with `--base`/`--head` [observed: commit `47fa178`, "passing them together silently discarded the range the user asked for"].
- `--repo`/`--post` only make sense with `--pr`.
- `--scope` and `--config-dir` are mutually exclusive.

`--context-file <path>` is orthogonal enrichment, not a source selector: it carries no `validateArgs` exclusivity rule and composes with any diff source [observed: `src/commands/review.ts` `parseArgs` `--context-file` case; no `contextFile` clause in `validateArgs`]. It injects the file's UTF-8 text into the reviewer prompts as an explicitly UNTRUSTED block (LLP 0004). The read happens ONCE in the command layer — before the source is built — and the byte-bounded raw text (`MAX_CONTEXT_FILE_BYTES` read ceiling; the 24k char cap is applied later, at prompt build in `src/core/prompts.ts`) is threaded into both `runReview` calls as `ReviewRunOptions.contextText`, so a routed `--scope` run does not re-read the file per scope [observed: `src/commands/review.ts` reads `contextText` before `makeSource`, passes it into the `--scope` and non-scope `runReview` calls]. A local read error FAILS LOUD: `ecr review` writes the error to stderr and sets `process.exitCode = 2`, because the user typed the path, so a typo or an oversized file is a mistake to surface rather than silently review without the context they asked for [observed: `src/commands/review.ts` `--context-file` catch → `process.exitCode = 2; return`]. An empty or whitespace-only file is NOT a read error: it WARNs to stderr and continues with no context section (both commands), rather than failing [observed: `src/commands/review.ts` and `src/commands/ci.ts` `!contextText.trim()` → warn, `contextText = undefined`]. This is the exact mirror of `ecr ci`, which warns and continues (below).

`--scope --post` posts under the derived marker `<rootTag>:<scope>`, taken from the ROOT config's tag via `scopedCommentTag(rootConfig.commentTag, scope)` [observed: `src/commands/review.ts:230`]. This is not a local convenience — it must match `ecr ci`'s per-scope derivation exactly, so a standalone local scope post and CI's per-scope post/clear/reconcile paths always target the identical comment. The schema ban on scope-level `commentTag` overrides (LLP 0006) is the only thing keeping the two derivations from ever diverging; relaxing that schema rule would silently break marker consistency between local and CI posts.

## Deferred Review Posting

`ecr review --save-review --repo owner/repo --pr N` separates the expensive model
run from the outward-facing GitHub write without changing the review between them.
After terminal preview it writes the exact verified `CoordinatorOutput` plus bounded
feedback records to an owner-only, versioned artifact under
`.expo-code-review/.runs/deferred/`. The artifact contains no credential. Saving is
PR-only, requires an explicit repo, and is mutually exclusive with immediate
`--post`; scopes and alternate config directories are rejected in v1 rather than
silently producing an artifact the post command cannot faithfully reconstruct
[observed: `src/commands/review.ts` `validateReviewArgs`,
`writeDeferredReviewArtifact`].

`ecr post-review --artifact P --repo owner/repo --pr N` performs no model call. It
loads config from the local checkout (the terminal user remains the trust principal),
strictly schema-validates and byte-caps the artifact, and requires four independent
bindings before any GitHub write: artifact target equals the explicit argv repo/PR;
the live PR head equals the reviewed 40-hex OID; the current comment tag,
break-glass marker, and feedback policy hash to the stored posting-policy
fingerprint; and the live break-glass check returns false. A break-glass API error
fails closed on this deferred path. Only then does it pass the stored review through
the ordinary `GitHubReporter`, preserving the single-comment lifecycle, dismissal
state, hidden review trace, links, pins, and feedback merge [observed:
`src/commands/post-review.ts`, `src/core/deferred-review.ts`].

The explicit repo/PR is deliberately repeated at post time. An artifact is data, not
authority: even a locally replaced artifact cannot redirect a generic “post this”
command to another PR. Head and policy drift require a fresh preview instead of
publishing stale findings or rendering them under rules the model run never saw.

## ecr ci: The Trusted-Root Run

`ecr ci` runs inside GitHub Actions with credentials, reading content authored by whoever opened the PR (including a fork PR reachable through the not-fork-restricted `issue_comment` `/review` workflow). Its structure is dictated by that threat model (LLP 0001).

**All reviewer configuration loads from the PR's immutable BASE commit, never the head.** `config.jsonc`, `routing.jsonc`, prompts, models, and the auth mapping are materialized from the base commit via the GitHub API, so a PR cannot edit the reviewer that evaluates it; config changes activate only after merge [observed: commit `601b19a`; `src/commands/ci.ts:162-181` `prepareTrustedConfigRootAsync`; `CI_USAGE` `src/commands/ci.ts:61-68`].

**It fails CLOSED.** If the base commit cannot be materialized, `ci` posts one terminal "this change was **not** reviewed" comment and stops — it never falls back to reading the checkout, because that fallback is exactly how a head checkout would smuggle config in [observed: `src/commands/ci.ts:149-152` comment, `166-180` catch → `postTerminalFailureNote` → `return`]. That terminal comment always uses the HARDCODED default tag `expo-ai-code-reviewer` and break-glass marker `/skip-review`, never the repo's configured ones, because the config that could customize them is precisely what failed to load [observed: `src/commands/ci.ts:231-251`]. A repo with a custom tag gets a fresh comment rather than an in-place upsert — the accepted degraded case.

**It never fails the PR's checks.** A reviewer error degrades to a posted failure comment, not a non-zero process exit [observed: `AGENTS.md`; `src/commands/ci.ts:354-373` legacy catch posts a summary; `src/commands/ci.ts:571-576` per-scope catch builds a `failureReview` placeholder instead of aborting the fan-out]. PR-facing comment text uses `publicFailureReason(error)`, not the raw `errorMessage`, so the credential and internal detail never leak into a comment (LLP 0002) [observed: `src/commands/ci.ts:176,365,575`].

**Automated reruns reuse unchanged complete results.** Before launching agents, CI hashes the review job's scoped diff and stable review inputs and compares it with the hash hidden in the newest author-verified reviewer comment. An exact match re-renders the stored result (so links, dismissals, and live annotation-only feedback still update) without spending model budget. Routed CI does this independently per scope. Manual `/review`/`--force`, stack-aware runs, model-backed feedback runs, partial/failed results, and truncated aggregate state all bypass reuse and run fresh. The hash contract and durable-state rules are owned by LLP 0005's Review Result Cache section.

**`--expect-head` pins the run to the commit the request named.** A workflow on a label event knows the commit the maintainer labeled (`github.event.pull_request.head.sha`), but `ecr ci` starts minutes later and reads the PR's head then, so a push in between would be reviewed with the secrets in place of the labeled code. With `--expect-head <sha>`, both CI paths compare the head they read with `<sha>` after the break-glass check and before any model call, and stop when it differs or is unknown (`expectedHeadMismatch` in [ci.ts](../src/commands/ci.ts)). The single-config path posts a `couldNotComplete` "not reviewed" note (`postNotReviewed`). The routed path only logs and removes the reviewer's ready label: its root comment holds the aggregate and its per-scope state, which a single-review render would replace, so a later `--scopes` run would lose the other scopes' results. A malformed flag (`--expect-head=<sha>`, an empty value, a short hash, the flag twice) is a usage error, never ignored, since an ignored flag would review an unpinned head without a word (`parseExpectHead`). Releases from before the flag ignore it like any unknown argument, so a workflow that passes it must pin a release that has it. The diff compares the same base and head commits the trees are checked out at (see [LLP 0008](./0008-sources-and-reporters.explainer.md#pr-head-materialization)), so a push after the check cannot swap the diff either [observed] (tests `src/__tests__/github-pr-head.test.ts`).

`--unsafe-config-from-head` is a deliberate escape hatch that reverses this model, loading config from the checkout. It is never scaffolded by `ecr init`, always prints a loud `⚠ SECURITY` warning, and is scheduled for removal on a minor version boundary [observed: `src/commands/ci.ts:85-91` `CI_USAGE`, `155-162` warning].

`--context-file` in CI takes the opposite read-error policy from `ecr review`, and the split is dictated by the never-fail-checks invariant. `ci` reads the file once before any fan-out and, on a missing/oversized/unreadable path, WARNs to stderr and continues with no context — it never fails, because a broken Atlantis-provided plan file must not turn the PR's check red [observed: `src/commands/ci.ts` `--context-file` read → stderr warn, no `exitCode`, `contextText` stays undefined]. The same reader (`readContextFile`, capped at `MAX_CONTEXT_FILE_BYTES`) backs both commands; only the catch policy differs — fatal locally, warn in CI. The byte-bounded raw text threads through the shared `CiRunOptions` into both `runLegacyCi` and `runRoutedCi`, and from there into every per-scope `runReview` as `contextText` (char-capped at prompt build) [observed: `src/commands/ci.ts` `CiRunOptions.contextText`; `runReview` calls in `runLegacyCi` and the fan-out loop].

One directory subtlety is load-bearing: the run-log / patch-workspace directory (`workspaceRunsDir`) anchors at the persistent workspace checkout, never the temporary trusted config root, because the workflow uploads `.expo-code-review/.runs/reviews.jsonl` from the workspace as an artifact and the trusted root is `cleanup()`'d before the job ends [observed: `src/commands/ci.ts:269-277`; commit `601b19a`]. Conflating the two directories would break the artifact upload.

## Trigger Policy and Break-Glass

Whether a PR gets reviewed at all is a config-not-YAML decision. The trigger policy (`skipLabel` / `label` / `all`) lives in `config.jsonc`'s `review.*` block, not in per-repo workflow YAML, because labels are write-gated to maintainers while `config.jsonc` historically could be read from the PR ref — keeping the skip decision immune to a PR author editing config to dodge review [observed: commit `1e9aea2`].

Label matching is exact-string, never substring: `ai-review:skip` must not satisfy an `ai-review` opt-in check. `shouldReview` compares whole label names (and a `label:<agent>` prefix variant), a fix for an earlier `join()`+substring form [observed: commit `1e9aea2`; `src/commands/ci.ts:720-736` `shouldReview`; test `src/__tests__/ci-trigger.test.ts`]. Labels are re-fetched live via `gh pr view` rather than trusted from the possibly-stale event payload, and a fetch failure returns `[]` so a label-read hiccup can never silently SKIP a PR that should be reviewed — the default leans toward reviewing [observed: `src/commands/ci.ts:678-682,683-711`].

A manual `/review` (the `--force` flag, or `GITHUB_EVENT_NAME === "issue_comment"`, which only reaches `ci` through the comment-command workflow) bypasses ONLY the trigger gate. Break-glass and the auth lock are separate checks that still apply [observed: `src/commands/ci.ts:746-751` `shouldBypassTriggerGate`, `760-777` `passesTriggerGate`; commit `69b841c`].

Break-glass is checked exactly once per CI run, on the root/aggregate comment marker, before any scope fan-out begins — not per-scope [observed: `src/commands/ci.ts:490-508`]. One check keeps the GitHub API calls down (rate-limit hygiene) and keeps the opt-out semantics repo-wide rather than per-team.

## Routed CI Fan-Out

When `routing.jsonc` exists, `ci` fans out internally: it assigns each changed file to exactly one scope (last-match-wins), reviews each active scope over only its files sequentially, and renders one aggregated comment (or one per scope). The routing model itself is LLP 0006; the decisions here are about how the *command* orchestrates it. With no `routing.jsonc`, dispatch falls to `runLegacyCi` and behavior is byte-identical to single-config mode [observed: `AGENTS.md`; `src/commands/ci.ts:193-200,279-282`].

The gating and identity rules are all "root config wins":

- The ROOT config's `review` trigger block gates the whole routed run — scope configs never widen or narrow whether the PR is reviewed [observed: `src/commands/ci.ts:443-454`].
- When `manifest.defaults.commentTag` diverges from the root `config.jsonc`'s tag, the ROOT tag wins and a warning is printed, so the existing comment's history and dismissals carry over instead of stranding under a fresh marker [observed: `src/commands/ci.ts:409-414`].
- Every id in `manifest.defaults.enforceAgents` must exist in the ROOT agent roster (the source of truth); a missing one is a loud, non-blocking skip of the whole run, never a silent no-op [observed: `src/commands/ci.ts:416-425`].

Two rules protect against the fan-out silently losing or mis-timing work:

- The passes budget divides across active scopes with a per-scope floor (`minScopeMinutes`). Scopes run sequentially, so N × floor is real wall-clock time; when the floor forces the total past `totalPassesMinutes`, the floor is kept and a loud warning is emitted, not a hard failure [observed: `src/commands/ci.ts:527-539`; commit `08026ea`].
- A partial `--scopes` re-run in aggregate ("single") mode is authoritative ONLY for the named scopes: it merges the other scopes' prior results out of the existing aggregate comment's stored state, so re-running one scope does not wipe the rest from the PR [observed: `src/commands/ci.ts:593-604,661-679`]. Mode-switch cleanup (deleting the other comment mode's stale comments) runs once on a full run but is skipped entirely for a partial run, which must never touch other scopes' live comments [observed: `src/commands/ci.ts:615-622,644-650`].

When no scope has anything to report — no changed file matched any scope, and (on a partial run) no prior scope results carry over from the stored aggregate state — the aggregate ("single") mode posts NOTHING: it deletes any stale aggregate comment from an earlier run instead of posting an empty "approve" review with a zero-row scope table [observed: `src/commands/ci.ts:605-616`, gate on `finalResults.length === 0` → `aggregate.clear()`]. A review of nothing is not a review, and a repo whose `routing.jsonc` deliberately scopes only part of the tree (no `**/*` catch-all) would otherwise get a contentless comment on every out-of-scope PR. The unmatched-files warning still goes to stderr in the job log, so coverage gaps stay visible to maintainers without notifying the PR author. Per-scope mode already behaved this way (a scope with no result gets its comment cleared, and no comment is ever created).

A scope whose config directory does not exist at the TRUSTED base commit — i.e. it is new in this very PR — is reviewed with the ROOT config instead of failing the whole run; the scope's own (PR-authored, untrusted-for-this-run) config activates only after merge [observed: `src/commands/ci.ts:541-559` `hasScopeConfig` fallback; commit `601b19a`; test `src/__tests__/trust-separation.test.ts`]. The known cost: a scope that is genuinely misconfigured (missing `config.jsonc` by mistake) is indistinguishable from an intentionally-new one — both fall back to the root config with a stderr note, never a hard CI failure.

A malformed `routing.jsonc` is a loud, NON-blocking stderr error that returns quietly, never a silent fallback to legacy single-config and never a crash [observed: `src/commands/ci.ts:183-191`]. In the job log this can superficially resemble a clean "no routing.jsonc" no-op, since `ci` never fails checks either way — the distinguishing signal is the stderr line, not the exit code.

## verify-config: The Config Guard

`ecr verify-config` is the CI trust guard that runs *before* the loaders are trusted, so it deliberately does not use them. It discovers configs via a plain recursive filesystem walk — NOT `git ls-files` and NOT `routing.jsonc`'s scope list — because a staged-but-unreferenced or untracked config directory carrying a rogue `auth` block can hide from git's index but not from an on-disk sweep [observed: `src/commands/verify-config.ts:58-63`; test `refuses an UNREFERENCED nested config dir carrying auth` in `src/__tests__/verify-config.test.ts`]. It parses every file with the real comment-aware JSONC parser (`stripJsonComments`/`stripTrailingCommas`) rather than regex-scraping, and fails closed — any parse error is itself a finding [observed: `src/commands/verify-config.ts:157-162`].

The rules it enforces:

- Root-locked keys (`auth`, `breakGlass`, `commentTag`) are refused in any non-root config [observed: `src/commands/verify-config.ts:176-193`]. This is the independent filesystem-sweep layer of a three-layer invariant (schema, loader, and this sweep) — it does not assume the schema or loader already ran, which is the point of it existing separately (LLP 0001).
- A `tokenEnv` may be declared in only ONE root-owned file. Multiple entries in one `auth` block are fine (multi-provider), but splitting declarations across two root files leaves no single honored source and lets a stale/staged second file smuggle a credential [observed: `src/commands/verify-config.ts:196-213`].
- With `ECR_EXPECTED_TOKEN_ENV` set, the declared `tokenEnv` set must equal it EXACTLY, as a set. Adding an extra credential name is refused exactly like repointing an existing one — a PR must not add, drop, or repoint credentials, not merely stay a superset [observed: `src/commands/verify-config.ts:227-249`].

The sweep ignores `ECR_CONFIG_DIR` on purpose: it always scans the entire repo. That env var changes which config the *loaders* honor, but `verify-config` is a security check, not a loader, so the two are intentionally decoupled [observed: `src/commands/verify-config.ts:278-286`]. One coupling worth naming: `CONFIG_FILENAMES` [observed: `src/commands/verify-config.ts:56`; `src/config/load.ts:86`] must mirror the filenames in `config/load.ts`; a new config file type added there without mirroring here becomes invisible to the sweep entirely — a fail-*open* gap despite the guard's overall fail-closed design.

## doctor and setup-auth

`ecr doctor` is a preflight that must never disagree with a real run. Its `resolveEngines` folds in every ROUTED SCOPE's agent and coordinator models, not just the root config's, because a scope can select an `anthropic/…` model even when the root config is OpenCode-only — without folding scopes in, doctor would report success while skipping the Claude CLI/login checks that scope's review actually needs [observed: `src/commands/doctor.ts:75-108` `resolveEngines`; test in `src/__tests__/doctor.test.ts`]. A scope config that fails to load is silently skipped here and surfaced later by a separate per-scope validation block — hoisting that try/catch out would make `resolveEngines` throw and abort the whole doctor run instead of degrading per-scope [observed: `src/commands/doctor.ts:98-106`].

doctor resolves auth the way real reviews do: a `routing.jsonc` `defaults.auth` OVERRIDES the root config's auth entirely (not merges), so the credential checks use the overridden value [observed: `src/commands/doctor.ts:165-174`]. And it mirrors `startClaudeCode`'s exact credential condition — an active `claude` subscription login OR a token value — so its verdict never reports `ok` where a real review would fail, nor `fail` where one would succeed; a missing credential is a hard `line(false)`, not a `warn()` (which never flips the exit code) [observed: `src/commands/doctor.ts:318-322`].

`ecr setup-auth` derives a plan from the repo's auth config via a pure `planFromAuth`, then guides local credential acquisition. Its decisions:

- It hands out only ACCESS tokens; the refresh token never leaves OpenCode's store, because OpenCode's refresh tokens are SINGLE-USE (rotation) and OpenCode is their sole legitimate consumer — a copy in a shell config or CI secret dies on the next rotation and can take the whole sign-in down with it [observed: `src/commands/setup-auth.ts:87-93`].
- The exported shell line single-quotes the token value so a token containing shell metacharacters (`$HOME`, `!`) is never expanded when sourced [observed: `src/commands/setup-auth.ts:127-131`; test in `src/__tests__/setup-auth.test.ts`].
- `anthropic` auth is always satisfied by the Claude Code CLI subscription-login flow regardless of the declared `mode` (oauth vs api-key) — mode is irrelevant for that provider [observed: `src/commands/setup-auth.ts:50-59`].
- A `meta` API-key entry is a manual-key plan: setup-auth points to the Meta AI developer portal and prints the configured `META_API_KEY` export, while doctor uses the same generic provider readiness check as the real review [observed: `src/commands/setup-auth.ts` `planFromAuth` / manual-key guidance; `src/core/auth.ts` `PROVIDER_KEY_ENV`].
- The two interactive logins run via `spawnSync` with `stdio: "inherit"` and `cwd: os.tmpdir()` — the tmpdir cwd keeps a possibly-untrusted checkout from becoming the login subprocess's working directory, and the `inherit` stdio is why these two calls cannot be converted to `exec.ts`'s capturing `run()` [observed: `src/commands/setup-auth.ts:200-203,256-259`]. `ecr attach` is interactive too, but it stays inside `exec.ts` via `spawnInherited` because the opened session needs the terminal (see [Session archive](#session-archive)).

## init and dismiss

`ecr init` scaffolds `.expo-code-review/` and optionally the CI workflow files (LLP 0009). `--token-env <name[,name…]>` bakes a non-default credential env into the two review-running workflows at scaffold time — validated (shape, `FORBIDDEN_TOKEN_ENVS`, duplicates) before any file is written, and refused with `--scope` or `--no-workflow` where it has no workflow to rewrite, and also refused (without `--force`/`--force-workflows`) when the review workflows already exist — existing files are skipped, not rewritten, so the flag would silently never reach CI while the summary claims the workflow references the new secret; `--force-workflows` is the surgical remedy that rewrites only the workflow YAML while leaving the adopter's tuned `config.jsonc`, prompts, and `agents/` untouched (`--force` rewrites the tuned files too, and shares the refusal below). The reverse is guarded too: a `--force-workflows`/`--force` run with no `--token-env` rewrites the workflows from the pristine (OpenAI) template, so it refuses when the existing review workflows already forward a non-default credential rather than silently reverting CI to `OPENAI_API_KEY` and running with an empty credential — naming `--token-env` again (or the default, to reset on purpose) is the explicit opt-in [observed: `src/commands/init.ts` `parseTokenEnvs`/`substituteTokenEnv`/`detectWorkflowTokenEnv`; why the mapping is baked statically: LLP 0009#what-ecr-init-scaffolds]. With `--scope`, it derives and validates the routing-scope entry (kebab-case name, config path) BEFORE creating any files on disk, specifically to stop a path-traversal `--scope ../../outside` from orphaning files outside the repo and to stop a bad-but-valid-looking name from making `routing.jsonc` unparsable, which would silently stop every future review [observed: `src/commands/init.ts:184-205`]. `appendScopeEntry` inserts the entry via manual bracket/string/comment-aware text scanning, not a JSON parse+stringify round-trip, so it preserves the user's comments and formatting; it is idempotent, and it places the separating comma after the last entry's real content, never inside a trailing `//` or `/* */` comment [observed: `src/commands/init.ts` `appendScopeEntry`].

`ecr dismiss` / `ecr undismiss` mutate only DISPLAY state. Dismissing a finding never re-runs the review — it moves the finding into a collapsed "Dismissed on this PR" section and the dismissal persists across future re-reviews [observed: `src/commands/dismiss.ts:13-15` USAGE; `applyDismissal` at `src/commands/dismiss.ts:98`]. Finding ids are sanitized to hex with `arg.replace(/[^a-f0-9]/g, "")`, which silently *mangles* a malformed id rather than rejecting it: a typo does not error, it just becomes a different (probably non-matching) id that reports as "unmatched" later [observed: `src/commands/dismiss.ts:49`]. There is no dedicated test for dismiss's argument parsing, so this behavior is easy to regress unnoticed.

## Session archive

A finished review can be reopened on any machine. Every pass is stored as the export JSON of the OpenCode version pinned in this package. That includes a Claude pass, which never opened OpenCode. `ecr attach` reads that file and opens the engine that matches the model recorded on the pass. An `anthropic/…` model opens in Claude Code. Any other model opens in the pinned OpenCode. The stored file stays unchanged.

A pass that opens in OpenCode is imported with the pinned `opencode` and then forked. The TUI shows the fork. The imported session stays unchanged. The import goes into a database file in the temp directory of that attach (`OPENCODE_DB`), not into the developer's own OpenCode database. An import replaces a session that has the same id, so an archive could otherwise change one of the developer's sessions, and every attach would leave a transcript behind. The login is not in that file, so a follow-up still uses this machine's login. [observed: `src/commands/attach.ts` `attachEnv`]

OpenCode's fork copies the messages and leaves the model and the agent empty. Attach writes both back from the export before the TUI opens. The model is the one recorded on the pass. That can differ from the model named in the repository config. A pass with no recorded model still opens. If writing the model fails, the transcript still opens and attach prints one line.

The prompt bar does not read that session model. It copies the last user message, and only when that message's agent is OpenCode's own `build` or `plan`. A review agent is neither, so the bar stays on the default model and the next question goes there. Attach rewrites that one message on the imported copy: the agent becomes `build`, and the model becomes the one recorded on the pass. The message text stays. The stored archive stays.

The bar also ignores a model whose provider is not connected. Attach names the recorded provider in the server config (`OPENCODE_CONFIG_CONTENT`). That lists the catalog models, so the bar can select the recorded one. It does not add a credential and it does not write `auth.json`. A follow-up still uses this machine's login for that provider. With no login, the question fails on the recorded model. [observed: `src/commands/attach.ts` `forkKeepingModel`, `exportForPromptBar`, `promptBarEnv`; `src/core/session-archive.ts` `sessionModelOf`]

A pass that opens in Claude Code starts a new `claude` conversation. The review runs with `--no-session-persistence`, so there is no Claude session to resume. Attach writes the stored transcript to a file in a temp directory of its own. Claude Code gets that directory with `--add-dir`, and a short note in `--append-system-prompt` names the file. The transcript holds a pull request diff, so its text is never part of the system prompt. It reaches the model only as the result of a file read. When the transcript is over 200,000 characters, attach keeps the end, where the findings are. `--model` is the id recorded on the pass, without the `anthropic/` prefix. The machine's Claude login applies, and so does `CLAUDE_CODE_OAUTH_TOKEN` when it is already set. Attach does not copy that token into OpenCode and does not set `ANTHROPIC_API_KEY`. `--safe-mode` and `--strict-mcp-config` keep the working directory's CLAUDE.md, hooks, and MCP servers from starting. `--safe-mode` still reads the working directory's `.claude/settings.json`, which can point the model request at another host with `env.ANTHROPIC_BASE_URL`. Attach passes `--setting-sources user`, so only the developer's own settings load. `--tools Read,Grep,Glob` leaves the follow-up with no tool that runs a command, edits a file, or uses the network. Attach does not copy `~/.claude` and does not pass `--resume`. [observed: `src/commands/attach.ts` `attachEngine`, `transcriptForClaude`, `claudeAttachNote`, `claudeAttachArgs`]

`runReview` keeps the session whose reply parsed. A pass that ran inside OpenCode is read with `opencode export` before the run closes the server and deletes its data directory. The export goes to a temp file, not to a pipe. Under Node, the pinned CLI exits before a pipe is drained, and a large export came back cut short. A Claude pass has no OpenCode session. The archive module builds the same JSON from the `claude -p` stream that run already read. A session titled `route` is the router and is left out. With no capture, the review records nothing. [observed: `src/core/opencode.ts`; `src/core/claude-code.ts`; `src/core/review.ts` `exportReviewSessions`; `src/core/session-archive.ts` `exportOpencodeSession`, `buildClaudeSessionExport`; `src/core/exec.ts` `RunOptions.stdoutPath`]

The zip is `index.json` plus one `opencode/<agent>.json` per pass. A row carries the agent, the title, the routing scope, the session id, the file, and the engine, so a second chunk, or the same agent in another scope, is a separate row. OpenCode sorts a session by id, so the message and part ids of a Claude export ascend in stream order. In a Claude tool input, `file_path`, `path`, and `filename` are rewritten. A path inside the review tree becomes relative to it. Any other absolute path becomes `(outside the review tree)`. The prompt and the tool outputs stay as they were, so a runner path can still appear there. [observed: `src/core/session-archive.ts`]

An export whose version is not the pinned OpenCode is refused. When the index records a plain release version, the message names that `ecr` version, because that release ships the OpenCode that can read the file. A zip over 80 MB is neither uploaded nor unpacked. An entry is unpacked only when it is read, and never past 128 MB. Attach checks every field of the index before it uses the file. Export and import children do not receive `GH_TOKEN` or the other forbidden token env vars, and the upload log has those values removed. One `opencode export` stops after 30 seconds. The exports of one `runReview` share two minutes, because the PR comment is waiting on them. Each routed scope is its own call. It has its own two minutes and exports only its own passes. A pass that failed to export is tried once more, then logged. Before that second try, the run closes the server and waits until nothing answers at its address, for 5 seconds at most. An upload still running after 5 minutes is logged as a failure, and its whole process group is stopped. The repository name is part of the release tag. A name git will not accept in a tag, such as `.github`, is skipped, and the log says why. [observed: `src/core/session-archive.ts`]

`ecr ci` uploads one `sessions.zip` after the PR comment is posted, and only when `SESSION_STORE_REPO` is set. Routed mode shares one capture, and each pass is filed under the scope that ran it. A cache hit, a break-glass skip, a head mismatch, and a thrown review upload nothing. When one routed scope throws, that scope's passes are dropped and the other scopes still upload. A failed upload is one log line. The check still passes. [observed: `src/commands/ci.ts`]

Every reader of the store can download a transcript, and a transcript holds source code. The upload first reads the store's visibility with `gh repo view`. A store that is not private gets no upload, and neither does a store whose visibility cannot be read. Both `gh` calls use `SESSION_STORE_TOKEN` when it is set. `ecr ci` takes that variable out of its environment before the review starts, so no model process inherits it. The name is also in `FORBIDDEN_TOKEN_ENVS`, so no config can use it as `auth.tokenEnv`. Without it, `gh` uses `GH_TOKEN`. The `GITHUB_TOKEN` of the workflow template cannot create a release in another repository, so a store needs its own token. [observed: `src/commands/ci.ts`; `src/core/session-archive.ts` `takeSessionStoreToken`, `assertPrivateStore`; `src/core/auth.ts` `FORBIDDEN_TOKEN_ENVS`]

`ecr attach` downloads that zip and opens one pass. The default is the first reviewer. `--session` selects any other pass by the session id in the index. An anthropic pass opens in Claude Code. Any other pass opens a fork of the imported OpenCode session. Archives are found by tag prefix, and the newest `publishedAt` is opened. The prefix is the pull request, or one head commit with `--sha`. `--run` keeps only the archive of that workflow run. A release's `createdAt` is the date of the commit under its tag, so it cannot put the uploads in order. Attach does not read the HEAD of the developer's checkout and does not change it.

A pull request can come from a fork, so attach puts its code on disk only when the developer asks. By default the pass opens in an empty temp directory and sees the transcript only. `--checkout` adds the commit recorded in the archive as a detached worktree in the temp directory of that attach. When the clone does not have that commit, attach fetches it from `origin` and names the fix if that fails. The fetch does not write `FETCH_HEAD` and does not recurse into submodules. The fetched objects stay in the clone. Before it opens the pass, attach checks that the archive's `headSha` is the head in its tag, and that it equals `--sha` when one was given. It prints the tag and the commit, because the newest archive of a pull request can be for an older head.

A hook or a filter of the clone would otherwise run inside the worktree, on PR content. A husky post-checkout hook, for example, can install the packages the PR names. git-lfs reads its server URL from the PR's `.lfsconfig`, so a smudge would send a request to a host the PR picks. `core.hooksPath=/dev/null` alone is not enough, because it does not turn off a hook defined in config (`hook.<name>.command`). So attach reads the `hook.*` and `filter.*` names from the clone's config. It turns each one off, with `core.hooksPath=/dev/null`, `core.fsmonitor=false`, and `GIT_LFS_SKIP_SMUDGE=1`. These go in `GIT_CONFIG_*` variables, so a git command that the follow-up session runs gets them too.

The PR's `.gitattributes` can also select a diff driver of the clone (`diff.<name>.textconv` or `diff.<name>.command`), and a later `git show` would run it. An empty value does not turn a diff driver off, because git then fails. So attach sets `GIT_ATTR_SOURCE` to the empty tree, and git reads no attributes from the worktree. That also keeps the PR from selecting a filter. A git that does not know the variable ignores it, and then only the hook and filter entries apply.

A symlink in the PR can point at a file outside the worktree. Removing such links once does not hold, because a later `git restore` puts them back. `core.symlinks=false` makes git write every symlink as a plain file that holds the target of the link, also in a later git command.

Attach can inherit git variables. Git sets `GIT_DIR` for an alias that runs inside a linked worktree, and git in the new worktree would then use that other worktree. `git -c` sets `GIT_CONFIG_PARAMETERS`, which git reads after `GIT_CONFIG_*`, so it could turn a hook on again. Attach removes the variables that `git rev-parse --local-env-vars` lists from the environment of its git calls and of the session. It keeps `GIT_CONFIG_COUNT` and adds its own entries after the ones already there.

The worktree is removed when attach ends. The exit cleanup is registered before the worktree is added. On a signal, or on the `SIGHUP` of a closed terminal, it deletes the worktree directory and its `.git/worktrees/<id>` entry. It finds that entry by its `gitdir` file, which names the worktree, so it never deletes the entry of another worktree. A `SIGKILL` skips the cleanup. Each attach writes its PID in its temp directory, and the next attach removes a temp directory whose PID is not running. Git then reports the worktree as prunable, and the next `--checkout` removes its entry. Attach never runs `git worktree prune`, which would also drop a worktree of the developer on a drive that is not mounted. [observed: `src/commands/attach.ts` `withoutLocalGitEnv`, `untrustedTreeGitConfig`, `withGitConfig`, `checkoutRecordedCommit`, `removeDeadAttachDirs`, `removeStaleCheckouts`, `removeCheckout`, `dropCheckoutSync`]

With `--checkout`, the working directory is PR content. Its `opencode.json` and `.opencode` are PR content, the same files the review scrubs (see [LLP 0001](./0001-trust-model.principles.md#read-root-scrubbing)). Attach sets `OPENCODE_DISABLE_PROJECT_CONFIG=1` on the import, the server, and the TUI, so an MCP server defined there does not start on the developer's machine. That switch does not cover `.claude/skills` and `.agents/skills`, so attach also sets `OPENCODE_DISABLE_EXTERNAL_SKILLS=1`.

OpenCode's own agents allow every tool, and the transcript holds a pull request diff. The attach server config sets `bash`, `edit`, `webfetch`, and `websearch` to `ask`. It sets them again on `build` and `plan`, because a permission on one agent wins over the shared one. One input is left. When the agent reads a file, the pinned OpenCode adds any `AGENTS.md`, `CLAUDE.md`, or `CONTEXT.md` from the directories between that file and the root, and no switch turns that off. Attach does not remove those files from the worktree, so that text can reach the model. It cannot run a command, edit a file, or use the network without an answer from the developer.

A language server starts on a file read, and a formatter after an edit, and neither asks. The pinned OpenCode resolves the TypeScript server from the working directory, which is PR content. Both are off unless the developer's own OpenCode config turns them on, and the attach server config wins over that config. So it sets `lsp` and `formatter` to `false`. [observed: `src/commands/attach.ts` `attachEnv`, `askFirstEnv`]

The local server can run shell commands, so each attach gives it a new `OPENCODE_SERVER_PASSWORD`. It also sets `OPENCODE_SERVER_USERNAME`, so a username from the shell cannot break the request attach sends. Only the TUI that attach starts has the password. Any other request gets HTTP 401. Text from the archive and from the release notes is printed with control characters removed. A signal ends `ecr attach` before its own cleanup runs. The handler in [exec.ts](../src/core/exec.ts) sends `SIGTERM` to the server and the TUI, which lets the TUI restore the terminal. It waits up to 3 seconds for them to exit, and then sends `SIGKILL`. The server leads its own process group, so the commands it started stop with it. The TUI stays in the foreground group of the terminal. Only then does the handler delete the temporary directory, which holds the transcript and the database file. A second signal does not wait. The server does not get the `SIGHUP` of a closed terminal, so attach handles that signal the same way. [observed: `src/commands/attach.ts`; `src/core/exec.ts` `onSignal`, `stopChild`]

The store repo, the reaper, and the `expo/expo` workflow are outside this CLI.
