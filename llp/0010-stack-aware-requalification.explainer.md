# LLP 0010: Stack-Aware Requalification

**Type:** Explainer
**Status:** Active
**Systems:** Sources, Engine, Prompts, Rendering, Config, Security
**Author:** Philippe Loulidi / Claude
**Date:** 2026-07-31
**Related:** [LLP 0000 System Map](./0000-expo-code-review-cli.explainer.md), [LLP 0001 Trust Model](./0001-trust-model.principles.md), [LLP 0002 Review Pipeline](./0002-review-engine-pipeline.explainer.md), [LLP 0004 Diff & Prompts](./0004-diff-noise-and-prompts.explainer.md), [LLP 0005 Verification & Rendering](./0005-verification-fingerprints-rendering.explainer.md), [LLP 0008 Sources & Reporters](./0008-sources-and-reporters.explainer.md)

The canonical stacked-PR flow reviews the bottom PR first. A finding like "you changed `parse.ts` but added no test" is correct *at that moment* and wrong a day later, once the author stacks a `parse.test.ts` PR on top. Stack-aware requalification lets the reviewer see that later PR and stop **blocking** on the absence — without ever hiding the finding. This doc explains the mechanism and, more importantly, why each guard exists; it does not restate the code.

The shape is: fetch a **paths-only** manifest of the open PRs stacked on top of this one (once per run), inject it into the **single coordinator call only**, let the coordinator annotate absence-style findings with `requalifiedBy`, then run a **deterministic, zero-LLM grounding pass** that strips any annotation that is forged, hallucinated, or touches a protected class. A requalified finding is never removed: it renders in its own section, is counted in a visible audit line, and is excluded only from the blocking decision. This is v1; a per-candidate patch-level LLM confirmation is deferred to v2.

## The Upstack Manifest

`ReviewSource` gains one optional method, `getStackContextAsync`, beside `prepareReadRootAsync` [observed] ([source.ts](../src/sources/source.ts) `ReviewSource`). It returns a `StackManifest` — a list of `{ number, title, authorLogin, files }` plus a `truncated` flag — or `null`. The return is deliberately two-valued, not three like `prepareReadRootAsync`: there is no "throw" case. **Any** failure (no repo, a `gh` error, a rate limit, a parse error, an empty stack) resolves to `null` [observed] ([github-pr.ts](../src/sources/github-pr.ts) `getStackContextAsync`, whole body wrapped in one `try/catch` → `null`). This is the inverted fail-open direction: breaking the walk buys an attacker only the status quo (findings stay blocking), so the safe default is "as if the feature were off". `LocalGitSource` omits the method, which makes `ecr review` over local git a structural no-op [observed] ([source.ts](../src/sources/source.ts): `memoizeSource` only exposes the method when the wrapped source defines it).

`memoizeSource` gains a fourth memo field so a routed CI run — which calls `runReview` once per scope — fetches the stack exactly once and shares it, the same rate-limit hygiene reason the read root and metadata are memoized (see [LLP 0008](./0008-sources-and-reporters.explainer.md)) [observed] ([source.ts](../src/sources/source.ts) `stackPromise`). Everything in the manifest is PR-author-controlled, so it is untrusted data end to end.

## Bounded, Guarded Upward Walk

The walk is upward only. A downstack (parent) layer's content is already merged into the materialized head tree the reviewers read, so a parent never produces a false "missing" finding this mechanism needs to fix. Children are the open PRs whose base branch is this PR's head; recursion follows each child's own head branch [observed] ([github-pr.ts](../src/sources/github-pr.ts) `fetchOpenChildren`, `walkUpstack`).

The IO and the logic are split on purpose. `walkUpstack` is a pure, exported function over two injected fetchers, so every bound and guard is unit-testable without `gh` [observed] ([github-pr.ts](../src/sources/github-pr.ts) `walkUpstack`; tests [stack-walk.test.ts](../src/__tests__/stack-walk.test.ts)). The bounds it enforces, and why each is load-bearing:

- **Same-repo, root included** — a child counts only when `head.repo.full_name` equals `owner/repo` [observed] ([github-pr.ts](../src/sources/github-pr.ts) `fetchOpenChildren` sets `sameRepo`). The REST pulls-list endpoint has no `isCrossRepository` field, so this comparison is the fork gate; a fork PR is dropped. The ROOT PR gets the same gate before the walk even starts: a fork PR's `headRefName` names a branch of the FORK, and using it as the pulls-list `base=` filter would match a same-named base-repo branch (a fork head called `main` would pull in every open PR targeting `main`), letting unrelated PRs into the manifest — so a cross-repo root (`isCrossRepository` from `gh pr view`) returns `null` outright [observed] ([github-pr.ts](../src/sources/github-pr.ts) `getStackContextAsync` cross-repo guard).
- **Same-author** — when `requireSameAuthor` (default true), a child counts only when its `user.login` equals the current PR's author [observed] ([github-pr.ts](../src/sources/github-pr.ts) `walkUpstack` same-author filter; author from `fetchPrTrustAnchors`). This closes cross-author poisoning: a push-access colleague opening a child PR on the victim's branch cannot inject paths. Teams running genuine multi-author stacks set `requireSameAuthor: false` from the trusted base — an explicit, base-committed choice.
- **Depth / width caps and a cycle guard** — `maxDepth` levels, `maxPrs` children per level, and a visited-branch `Set` so a branch cycle can't loop [observed] ([github-pr.ts](../src/sources/github-pr.ts) `walkUpstack`). Per child, files are fetched with `--paginate` and capped at `maxFilesPerPr`, setting `truncated` when the cap bites [observed] ([github-pr.ts](../src/sources/github-pr.ts) `fetchChildFiles`).

`--method GET` on the pulls list is mandatory (else `gh` POSTs), and a per-element `--jq` yields NDJSON that stays valid when `gh` concatenates pages — unlike a bare `--paginate`, which concatenates JSON arrays into invalid JSON (the same trap the reporter's manual pagination avoids, [LLP 0008](./0008-sources-and-reporters.explainer.md)) [observed] ([github-pr.ts](../src/sources/github-pr.ts) `fetchOpenChildren`).

## Requalification Schema and Fingerprints

`Finding` gains an optional `requalifiedBy: { prNumber, file, reason }` [observed] ([schema.ts](../src/core/schema.ts) `FindingSchema`). It rides the coordinator output schema for free, since that schema reuses `FindingSchema`. Critically, `fingerprintFinding` is **untouched** — it keys on `file`/`category`/`evidence`, never on `requalifiedBy` [observed] ([schema.ts](../src/core/schema.ts) `fingerprintFinding`). If requalification entered the fingerprint, a maintainer's dismissal would silently lapse the moment a finding was requalified, and the embedded-state identity would churn. Keeping it out means requalification is purely an annotation over an otherwise-stable finding identity.

## Coordinator-Only Injection

The manifest is wired into `buildCoordinatorTask` and nowhere else — a new parameter after `coverageNotes`, threaded through `coordinate()` [observed] ([prompts.ts](../src/core/prompts.ts) `buildCoordinatorTask`; [coordinator.ts](../src/core/coordinator.ts) `coordinate`). `buildReviewerTask` and `buildCrossCuttingTask` are byte-identical to before [observed] (tests [stack-prompts.test.ts](../src/__tests__/stack-prompts.test.ts) assert the fan-out builders are unchanged). Two reasons this placement matters: the wide fan-out (N agents × M chunks) carries **zero** stack bytes, so the cost is one small block in one call per scope, not a multiplier; and only the coordinator ever emits `requalifiedBy`, so a prompt-injected reviewer can never self-requalify — it never sees the manifest.

The block is defended like every other untrusted input, plus one addition. Titles **and** paths flow through `flattenUntrusted`, which collapses newlines per value [observed] ([prompts.ts](../src/core/prompts.ts) `stackContextSection`). A git filename may legally contain a newline, so without this a path like `a\n----- END UPSTACK MANIFEST -----` could forge the closing fence; collapsing the newline keeps the whole path on one line. On top of that, a dedicated boundary regex strips any line matching the new marker, mirroring `CONTEXT_FILE_BOUNDARY`, and is re-applied after the head/tail cap because the tail slice can promote a forged marker hidden behind a prefix to a line start [observed] ([prompts.ts](../src/core/prompts.ts) `UPSTACK_MANIFEST_BOUNDARY`, `capStackManifest`; test [stack-prompts.test.ts](../src/__tests__/stack-prompts.test.ts) forges a newline-bearing filename). The injection-defense prose sits outside the fence, matching the PR_TITLE/PR_BODY treatment. The cap is a flat ~4000 chars head+tail, so cost stays constant regardless of stack depth or width [observed] ([prompts.ts](../src/core/prompts.ts) `STACK_MANIFEST_MAX_CHARS`).

The trusted prose tells the coordinator the rules: requalify only absence-style findings (missing/not-updated/not-regenerated), never a defect visible in the diff; match by name correspondence (`foo.ts` ↔ `foo.test.ts`, a model change ↔ `migrations/*`); cite the exact manifest path; never touch critical, secrets, or security findings [observed] ([prompts.ts](../src/core/prompts.ts) `stackContextSection`). The prose is a request, not a guarantee — the grounding pass is what enforces it.

## Grounding and the Decision

`groundStackRequalification` runs between the verify block and `applyInlineIgnores`, preserving the load-bearing verify → ground → suppress → reconcile order [observed] ([review.ts](../src/core/review.ts) call site between verify and suppress; ordering constraint from [LLP 0002](./0002-review-engine-pipeline.explainer.md)). It is pure string membership over data ecr fetched itself — **zero LLM** — so forged citations and protected classes are handled even with a weak or prompt-injected coordinator. It **strips** `requalifiedBy` (leaving the finding fully intact and blocking) when any of:

- the cited `(prNumber, file)` is not an **exact** normalized member of the manifest. Normalization is repo-root-relative — strip a leading `./` or `/`, trim — then exact string equality, no substrings and no basenames (`a.ts` must not match `data.ts`) [observed] ([review.ts](../src/core/review.ts) `normalizeManifestPath`, `groundStackRequalification`). A debug line is emitted on every strip so a silent under-fire (e.g. a monorepo path-frame mismatch) is diagnosable.
- the finding is `critical`, or category `secrets` or `security`. The security category is excluded wholesale because a warning-severity security finding is exactly the class an attacker most wants demoted [observed] ([review.ts](../src/core/review.ts) `groundStackRequalification`).
- the finding's **file** carried a pre-coordination critical/secrets/security reviewer finding. This is the **severity lock**: locked files are captured from the raw reviewer findings *before* `coordinate()` runs, keyed by normalized file path [observed] ([review.ts](../src/core/review.ts) `buildPreCoordinationFileLocks`, built after the fan-out and before coordinate). Without it, a coordinator steered into "downgrade critical→warning, then requalify" would slip a real critical past the carve-out. The key is the file alone, NOT a content fingerprint: the coordinator legitimately re-categorizes and paraphrases findings, and `fingerprintFinding` hashes category + evidence, so a fingerprint-keyed lock would miss a downgraded-then-reworded critical. Over-locking a whole file only keeps findings blocking — the feature's fail direction.

Then `decisionAfterRequalification` re-derives the decision over the still-**blocking** (non-requalified) subset — the parallel of `decisionAfterVerification` [observed] ([review.ts](../src/core/review.ts) `decisionAfterRequalification`). Because grounding strips `requalifiedBy` from every critical, a requalified finding is never critical, so the later `decisionAfterVerification` inside the suppression block cannot re-escalate past the softened decision — a property pinned by test [observed] ([stack-grounding.test.ts](../src/__tests__/stack-grounding.test.ts)). Finally the reconcile trigger is extended to fire when the decision changed **or** findings were removed, since requalification softens the decision with no count drop and a count-only trigger would leave the summary contradicting a now-softer decision [observed] ([review.ts](../src/core/review.ts) reconcile trigger).

## Rendering in All Three Paths

Requalified findings render in a collapsed "🔁 Addressed in stacked PRs (N)" section beside the Dismissed section, in **both** `renderMarkdown` and `renderAggregateMarkdown`, and are excluded from the main severity list and the scope's blocking count [observed] ([render.ts](../src/core/render.ts) `renderMarkdown`, `renderAggregateMarkdown`). The single visibility rule the whole feature rests on: a mandatory one-line audit note in the OPEN body naming the addressing PRs [observed] ([render.ts](../src/core/render.ts) `requalificationAuditNote`). Requalification's only effect on a real finding is moving it out of the blocking set, so it must never be silent — the count and PR numbers show above the fold, and every reason names its `#N`.

`requalifiedBy` rides `encodeState` automatically as a `Finding` field, and the aggregate embeds requalified findings in its per-scope state exactly like dismissed ones, so a `/dismiss` re-render round-trips them and the addressed section survives [observed] ([render.ts](../src/core/render.ts) aggregate `stateScopes`; the reporter's `applyDismissal` re-render path, [github.ts](../src/reporters/github.ts)). The aggregate's worst decision is computed over the per-scope decisions, which are already requalification-adjusted upstream in `review.ts`, so a scope whose only findings are requalified contributes an `approve` [observed] ([render.ts](../src/core/render.ts) `worstDecision`).

## Config and CLI Surface

A root-only `stack` block joins `auth`/`breakGlass`/`commentTag` on the scope-override exclusion list — declaring it in a scope config fails at the Zod level [observed] ([schema.ts](../src/config/schema.ts) `ReviewConfigSchema.stack`, `ScopeReviewConfigSchema`). One PR has one stack; per-scope divergence is meaningless and a silent-override hazard. It defaults to `enabled: false`: a suppression-adjacent feature earns trust with field data first.

The trust principal differs by command. Under `ecr ci`, config loads from the PR's immutable base commit, so `stack.enabled` there is a trusted-base decision a PR cannot change; the feature auto-enables from it, and `--no-stack-aware` is an argv escape hatch that forces it off for one run [observed] ([ci.ts](../src/commands/ci.ts) `resolveStackWalk`). All stack failures are stderr warnings, never check failures — the source fails open, so nothing propagates. Under `ecr review --pr`, config comes from the local checkout, which is **not** a trusted base, so the feature is off unless the user passes `--stack-aware` explicitly — the person typing the flag is the trust principal [observed] ([review.ts](../src/commands/review.ts) `--stack-aware`). No path exists where head-controlled config activates the feature.

## Residual Exposure (v1) and v2

The accepted v1 residual: a same-author, same-repo, real child PR that genuinely touches the cited path can get a warning/suggestion-level, non-security finding demoted out of the blocking set without proof the touch actually fixes it. The finding stays rendered and counted; only its blocking status changes. Under today's policy only criticals drive `request_changes`, and grounding never lets a critical be requalified, so the v1 effect on real findings is visibility-tier — which is exactly why the audit count line is mandatory, not optional. v2 closes the residual with a per-candidate, no-tools patch-level confirmation (read the addressing PR's actual patch before believing "addressed"), bounded by `maxConfirmations` and failing open toward keeping the finding blocking; it is out of scope for this commit.
