**Author:** Philippe Loulidi / Claude
**Date:** 2026-07-30
**Related:** [LLP 0000 System Map](./0000-expo-code-review-cli.explainer.md), [LLP 0001 Trust Model](./0001-trust-model.principles.md), [LLP 0005 Verification & Rendering](./0005-verification-fingerprints-rendering.explainer.md), [LLP 0007 CLI & CI](./0007-cli-commands-and-ci.explainer.md)

Sources are where the diff comes from; reporters are where the result goes. The review core in between is mode-agnostic: local mode wires a [`LocalGitSource`](../src/sources/local-git.ts) plus a [`TerminalReporter`](../src/reporters/terminal.ts), CI mode wires a [`GitHubPRSource`](../src/sources/github-pr.ts) plus a [`GitHubReporter`](../src/reporters/github.ts), and the code between them is identical (AGENTS.md: "Core paths must work in both local mode and CI mode"). Everything below is about the seams — the parts where the two modes have to differ, and the decisions that keep those differences from leaking into the core or opening a trust hole. This doc explains why the seams are shaped the way they are; it does not restate the code.

## The ReviewSource Contract

`ReviewSource` is three methods: `getMetadata`, `getChangedFiles`, and an optional `prepareReadRootAsync` ([source.ts:8-29](../src/sources/source.ts)). The first two are obvious. The third is where the design work is, and its return signal is deliberately three-valued.

`prepareReadRootAsync` materializes the exact tree the review should READ from, because the diff is authoritative but the agents also read surrounding source and the verifier re-reads cited files — those reads must hit the right versions, not whatever happens to be checked out [observed] ([source.ts:12-26](../src/sources/source.ts)). Its outcomes are not "success or failure". They are three distinct things and collapsing any two is a bug:

- **A returned handle** — a tree was materialized; chdir into `handle.dir`, and the caller MUST call `handle.cleanup()` in a `finally` [observed] ([source.ts:34-35](../src/sources/source.ts): "always called in a finally").
- **`null`** — a deliberate, safe fall-through meaning "nothing to materialize", review the current checkout [observed] ([source.ts:20-23](../src/sources/source.ts)).
- **A thrown error** — a real failure. The source does not decide what that means; the *caller* does, per mode [observed] ([source.ts:23-26](../src/sources/source.ts)).

The null-vs-throw split is load-bearing, not an implementation detail. `null` is "fine, use the checkout"; a throw is "something went wrong". `resolveReadRoot` in the review core dispatches on exactly this: in CI a throw fails the run closed, in local mode a throw is a soft, logged fallback to the user's own checkout (an acceptable read root on your own machine), and `null` is always fine [observed] ([source.ts:20-26](../src/sources/source.ts); enforced at `src/core/review.ts` `resolveReadRoot`; tests `src/__tests__/trust-separation.test.ts:218-248`). A well-meaning refactor that "just returns null on any failure to be safe" would silently defeat CI's fail-closed guarantee for the trust boundary — the exact thing that must not happen. Throw is for real failures; null is only for the "no owner/repo configured" case.

**Rejected alternative — per-scope materialization.** A CI run fans one PR out across many scopes (per-package configs). Materializing the PR-head worktree once per scope would mean N `gh pr diff` calls and N worktrees for one PR, which is rate-limit abuse. `memoizeSource` wraps a source so `getMetadata`/`getChangedFiles`/`prepareReadRootAsync` each run exactly once and are shared across all the sequential `runReview` calls [observed] ([source.ts:38-74](../src/sources/source.ts); call sites `src/commands/ci.ts`, `src/commands/review.ts`). The subtle part is cleanup: the wrapped `prepareReadRootAsync` hands each scope a *different* handle object whose `cleanup()` is a no-op, and the real teardown is deferred to a single `dispose()` [observed] ([source.ts:55-72](../src/sources/source.ts)). This has to be this way — if cleanup were real per-call, the first scope to finish would delete the worktree out from under the scopes still running. Do not "simplify" the per-scope no-op cleanup into a real one, and do not call `dispose()` per scope; `dispose()` runs once, after the last scope [observed] ([source.ts:66-72](../src/sources/source.ts)).

## PR-Head Materialization

For a GitHub PR the read root is the PR head, materialized as a **detached worktree pinned to the immutable head OID** — not a branch or ref name [observed] ([github-pr.ts:149-192](../src/sources/github-pr.ts); commit dbd52ef "Review the PR-head tree on --pr runs (verification fidelity)"). The OID comes from `gh pr view --json headRefOid`, and every materialization pins to that OID so a rename, force-push, or deleted head between API calls cannot swap the tree ([github-pr.ts:66-68](../src/sources/github-pr.ts)). The fetch uses `refs/pull/<n>/head`, which the base repo hosts even for fork PRs [observed] ([github-pr.ts:152-153, 179-182](../src/sources/github-pr.ts)).

The checkout targets the specific OID, never `FETCH_HEAD`. `FETCH_HEAD` would work most of the time, but if the ref moved between the metadata fetch and the worktree fetch, `FETCH_HEAD` would silently materialize a *different* tree than the one the diff was fetched for; pinning to the OID makes that case fail loudly instead [observed] ([github-pr.ts:125-128](../src/sources/github-pr.ts)).

**`isCommitOid` is the single gate.** Only a full 40-hex OID (`/^[0-9a-f]{40}$/i`) may reach `git worktree add`/`git fetch` in the materialization paths [observed] ([github-pr.ts:19-23, 110-112](../src/sources/github-pr.ts)). This is deliberately narrow and does two jobs at once. It closes the metadata-fetch-vs-materialization TOCTOU race (only the exact fetched commit is checkable-out), and it blocks argument injection through a crafted ref string — a value like `--upload-pack=evil` is not 40 hex chars, so it never reaches git [observed] ([trust-separation.test.ts:193-204](../src/__tests__/trust-separation.test.ts) checks the injection case). Widening `isCommitOid` to accept short SHAs or refs "for convenience" reopens both holes at once.

**Scrub before use.** The materialized head tree is attacker-controlled fork content, and it becomes the OpenCode/Claude runtime's project root — a process that holds the model credential and `GH_TOKEN`. That runtime auto-discovers and can execute or inject from ambient config, so the tree is scrubbed of `opencode.json{,c}`, `.opencode/` plugins, `AGENTS.md`/`CLAUDE.md`, `.claude/`, `.mcp.json`, `.cursor*`, and `.env*`, and out-of-tree symlinks are stripped in the same pass, BEFORE the tree is handed over [observed] ([github-pr.ts:155-162, 184-185](../src/sources/github-pr.ts); commit 601b19a "isolate the runtime from PR-head config"; commit 93aaf30 "Strip out-of-tree symlinks when materializing the PR-head read root"). The scrub policy itself lives in `src/core/scrub.ts`, not here — the source calls it but does not own the list of what counts as ambient config. See [LLP 0001](./0001-trust-model.principles.md) for the trust reasoning behind the scrub.

**A half-scrubbed tree must never be returned.** If either scrub step throws partway through, `prepareReadRootAsync` cleans up the worktree and re-throws rather than handing back a partially-cleaned root [observed] ([github-pr.ts:183-190](../src/sources/github-pr.ts), comment verbatim). A tree that is 90% scrubbed is not 90% safe; it is unsafe.

**Token handling.** Git fetches APPEND a gh credential helper (`-c credential.helper=!gh auth git-credential`) rather than replacing the credential config [observed] ([github-pr.ts:26-32, 120](../src/sources/github-pr.ts)). Appending, not overriding, has two reasons: `GH_TOKEN` flows via the credential-helper protocol so it never lands in argv or `.git/config` (works even under `persist-credentials: false`), and a developer's own existing helpers still run first, so local behavior is unchanged [observed] ([github-pr.ts:26-30](../src/sources/github-pr.ts); commit 601b19a). Replacing it with a sole `credential.helper` override would break developer machines that rely on their own helpers.

## The Trusted Base Root

`prepareTrustedConfigRootAsync` materializes the PR **BASE** commit — not the head — as a separate worktree [observed] ([github-pr.ts:194-210](../src/sources/github-pr.ts); commit 601b19a). This is the whole trust story of CI in one method. Review policy, prompts, routing, and auth mapping all load from the base tree, so a PR cannot change the reviewer that evaluates it — config changes only take effect after they merge into the base branch [observed] ([github-pr.ts:195-197](../src/sources/github-pr.ts); commit 601b19a: "loads all review configuration from the PR's immutable base commit, never from the PR head"). The base tree is trusted, so it is *not* scrubbed; the head tree is untrusted, so it is. Two worktrees, two trust levels, by construction.

The base OID is fetchable by SHA even though the base ref may have moved since the API call, because GitHub serves any reachable SHA of the base branch — the same mechanism `actions/checkout` uses for `ref:` pins [observed] ([github-pr.ts:206-208](../src/sources/github-pr.ts)). Materialization here always throws on failure; `ecr ci` must fail closed with one terminal comment, never fall back to the checkout [observed] ([github-pr.ts:198](../src/sources/github-pr.ts); commit 601b19a).

`src/commands/ci.ts` is the only caller of `prepareTrustedConfigRootAsync` [observed] (sole call site: [ci.ts:164](../src/commands/ci.ts)). It anchors the trusted base worktree separately from the scrubbed head read root and keeps the run-log/patch workspace anchored at the CI workspace, not at the ephemeral trusted root, so artifact upload paths keep resolving. The mechanics of the ci command live in [LLP 0007](./0007-cli-commands-and-ci.explainer.md).

## Local Git Source

`LocalGitSource` has no network calls; it reads local git state and computes its own diff base [observed] ([local-git.ts:17-21](../src/sources/local-git.ts)). Three small decisions carry the weight.

**Default branch resolution** tries `origin/HEAD` via `symbolic-ref` first, then falls back through a fixed guess list (`origin/main`, `origin/master`, `main`, `master`), then `main`, because not every checkout has `origin/HEAD` set [observed] ([local-git.ts:31-50](../src/sources/local-git.ts)).

**Diff base is `merge-base(defaultBranch, HEAD)`, not the branch tip.** This scopes the review to the current branch's own changes and excludes commits merged into the default branch after the feature branch diverged — you review what you wrote, not what trunk moved on to [observed] ([local-git.ts:53-68](../src/sources/local-git.ts)).

**Untracked files are diffed without mutating the index.** Running a review must have no side effects on the user's working state, so untracked files are synthesized as add-diffs via `git diff --no-index -- /dev/null <file>` rather than being staged [observed] ([local-git.ts:101-103, 114](../src/sources/local-git.ts)). The listing uses `git ls-files -z` (NUL-terminated) so filenames containing newlines parse correctly [observed] ([local-git.ts:106-107](../src/sources/local-git.ts)), and the `--` separator before the filename stops a name beginning with `-` from being read as a git option — argument injection through an untracked filename [observed] ([local-git.ts:112, 114](../src/sources/local-git.ts)).

## GitHub Reporter Identity

The reporter maintains exactly one PR comment and is comment-only — it never touches the review-thread / GitHub "reviews" APIs, by explicit design [observed] ([github.ts:77-82](../src/reporters/github.ts)). The hard problem is: which comment on the PR is *ours*?

**Author + marker, never marker alone.** The comment marker is a hardcoded public literal, readable in the base-branch config, so anyone who can comment on the PR (including the untrusted PR author) could post a comment carrying the marker plus a forged embedded review state. A newest-marker-wins lookup would adopt that state and carry its `dismissed` list forward, silently suppressing real findings. So a comment counts as ours only if it carries the marker AND was authored by `ownLogin` — GitHub sets a comment's author from the authenticated identity and it cannot be spoofed [observed] ([github.ts:51-75](../src/reporters/github.ts); commit 93aaf30: "identify our own comment by author + marker, not the public marker alone, so a forged comment can't carry review state forward"; regression tests `src/__tests__/github-reporter.test.ts:25-34`). Any rewrite that reintroduces marker-only matching reopens this forged-dismissal-state attack.

**Fail closed on unresolvable identity.** `resolveOwnLogin` tries `gh api user --jq .login` first (works for a user/PAT token), and falls back to the literal `github-actions[bot]` only under GitHub Actions, because the default `GITHUB_TOKEN` is an installation token for which `/user` returns 403 [observed] ([github.ts:91-117](../src/reporters/github.ts)). When neither resolves, `ownLogin` is `null` and `selectOwnComments` treats NOTHING as ours [observed] ([github.ts:69-71, 114](../src/reporters/github.ts): `if (!ownLogin) return []`; test `github-reporter.test.ts:46-50`). It does not degrade to marker-only matching; it refuses to claim anything.

**Full-tag marker matching.** `<!-- tag -->` is checked as a whole tag, not as a substring, so a root marker and a scoped marker `<!-- tag:scope -->` cannot cross-match — this is the "reviewdog #1911 lesson", a known bug class in other PR-comment tools where prefix-matching markers collide across scopes [observed] ([github.ts:180-185](../src/reporters/github.ts), citing the lesson verbatim). Deletion is scoped strictly to author-verified comments: `clear()` and the upsert's duplicate cleanup only ever delete comments returned by `selectOwnComments`, never a look-alike carrying the same marker from someone else [observed] ([github.ts:186-192, 351-366](../src/reporters/github.ts)).

## Comment Lifecycle

**One live comment, converged by upsert.** `upsertComment` patches the newest of our own marker comments in place and deletes any older duplicates, so the review converges to a single comment across re-reviews instead of accumulating one per run [observed] ([github.ts:351-371](../src/reporters/github.ts)).

**Pagination goes to the end.** `fetchAllComments` paginates manually rather than using `gh api --paginate`, because `--paginate` concatenates each page's JSON array back-to-back into invalid JSON [observed] ([github.ts:302-303](../src/reporters/github.ts)). It must page all the way to the end because the issue-comments endpoint does not honor `sort`/`direction` and always returns oldest-first — our own most recent comment or a recent `/skip-review` break-glass comment can otherwise fall outside a single 100-comment window, causing duplicate posted comments and missed break-glass detection [observed] ([github.ts:303-307](../src/reporters/github.ts)). "Stop once we find a comment with our marker" would reintroduce exactly that bug, since the first match could be a stale comment. Pagination is capped at 30 pages (3000 comments) as a safety bound against a pathological PR, not a limit real PRs approach [observed] ([github.ts:297-299](../src/reporters/github.ts)).

**The comment is the durable store.** Review state — findings, dismissals, per-scope results — is embedded in the posted comment body itself (parsed via `parseReviewState`), not in a side-channel database, so `report()` and `applyDismissal()` are stateless across process invocations [observed] ([github.ts:145-154, 242-288](../src/reporters/github.ts)). Dismissals recorded in the existing comment are carried forward before re-rendering, so a maintainer's per-PR dismissals survive re-reviews instead of resetting on every push [observed] ([github.ts:145-151, 273-280](../src/reporters/github.ts)). `applyDismissal` validates added fingerprints against the CURRENT review's valid set before accepting them, and the valid namespace is scope-aware: scoped fingerprints for an aggregate comment, plain fingerprints otherwise, splitting the input into matched/unmatched rather than trusting caller-supplied fingerprints [observed] ([github.ts:258-271](../src/reporters/github.ts)). It throws — never silently no-ops — when there is no existing reviewer comment, or when the existing comment predates the embedded-state feature; the caller must run a review first [observed] ([github.ts:248-257](../src/reporters/github.ts)). The fingerprint scheme itself comes from the coordinator, not the reporter (see [LLP 0005](./0005-verification-fingerprints-rendering.explainer.md)).

**Break-glass gates on association, not authorship.** `checkBreakGlass` looks for the break-glass marker on a comment whose `author_association` is `OWNER`, `MEMBER`, or `COLLABORATOR` [observed] ([github.ts:40, 129-137](../src/reporters/github.ts)). The point is that a *maintainer* can post it to skip review — but a random external commenter cannot skip review just by posting the marker string. This is the one `Reporter` method that runs ahead of `report()`, consumed by `src/commands/ci.ts` before a review even starts.

**Body I/O goes through a tempfile.** `createComment`/`patchComment` write the JSON body to a temp file and pass it via `gh api --input <path>`, never on argv and never through a shell, avoiding argv length limits and shell injection on arbitrary finding text [observed] ([github.ts:373-418](../src/reporters/github.ts)). After every upsert, the exact posted body is mirrored into the GitHub Actions step summary — because the PR comment is edited in place across re-reviews, the step summary is the only per-run record of what was posted at that moment [observed] ([github.ts:368-370](../src/reporters/github.ts)).

**Links fail soft.** `linkContextAsync` can be prebuilt and injected once so a CI fan-out builds one diff-lines + base-SHA context for all scopes instead of one pair of `gh` calls per scope — the reporter-side mirror of `memoizeSource` [observed] ([github.ts:33-37, 200-205](../src/reporters/github.ts)). Both underlying fetches fail soft: a missing diff index degrades in-diff findings to plain-text `file:line`, a missing base SHA degrades out-of-diff findings the same way — never a dead link, never a hard failure of the whole report [observed] ([github.ts:194-235](../src/reporters/github.ts); commits f9fecd5, 9446b42). This follows the repo rule that `ecr ci` must never fail a PR's checks on reviewer error [observed] (AGENTS.md: "`ecr ci` must never fail a PR's checks — reviewer errors degrade gracefully").

## Terminal Reporter

The terminal reporter writes the primary report to **stdout** (progress and logging go to stderr) specifically so `ecr review > out.txt` captures a clean report and shell redirection works as expected [observed] ([terminal.ts:45-47](../src/reporters/terminal.ts)). It maps `review.decision` to a process exit code via `decisionExitCode`, which is what makes it usable as a pre-push/pre-commit gate; `--json` disables color and `noFail` forces exit 0 [observed] ([terminal.ts:28-32, 38, 49](../src/reporters/terminal.ts)). Color is enabled only on a TTY and only when not `--json` [observed] ([terminal.ts:38](../src/reporters/terminal.ts): `!options.json && Boolean(process.stdout.isTTY)`) — naively coloring whenever output is not JSON, ignoring `isTTY`, would corrupt piped or redirected output with ANSI codes.

`checkBreakGlass` is optional on the `Reporter` interface and CI-only by contract; local reporters omit it and callers treat a missing method as `false`, keeping local mode's contract simpler than CI's [observed] ([reporter.ts:5-10](../src/reporters/reporter.ts)). That asymmetry is intentional: break-glass is a CI trust affordance and has no meaning on a developer's own machine.
